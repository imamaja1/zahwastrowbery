# PRD — Sistem Penjualan Buah

**Versi:** 1.0
**Status:** Draft
**Framework:** Laravel 13
**Frontend:** React + Inertia.js
**Database:** MySQL
**Authentication:** Google Login
**Payment:** QRIS, COD, Transfer + Bukti Pembayaran
**NamaSistem:**ZahwaStrowbery

---

# 1. Gambaran Umum

Sistem Penjualan Buah adalah aplikasi web untuk melakukan penjualan berbagai jenis buah dengan pilihan kemasan, ukuran, dan satuan yang fleksibel.

Sistem memungkinkan pelanggan untuk:

* Login menggunakan akun Google.
* Melihat daftar buah.
* Melihat variasi produk.
* Memilih kemasan.
* Memilih ukuran.
* Memilih satuan.
* Menambahkan produk ke keranjang.
* Melakukan checkout.
* Memilih metode pembayaran.
* Mengupload bukti pembayaran untuk transfer.
* Melihat status pesanan.
* Melihat riwayat transaksi.

Admin dapat:

* Mengelola buah.
* Mengelola kategori buah.
* Mengelola jenis kemasan.
* Mengelola ukuran.
* Mengelola satuan.
* Mengelola variasi produk.
* Mengelola stok.
* Mengelola transaksi.
* Memverifikasi bukti pembayaran.
* Melihat grafik penjualan.

---

# 2. Tujuan Sistem

## 2.1 Tujuan Utama

Membangun sistem penjualan buah berbasis web yang mampu menangani produk dengan variasi penjualan yang fleksibel.

Sistem tidak menganggap semua buah dijual dengan satuan yang sama.

Contoh:

* Apel dapat dijual per Kg.
* Apel dapat dijual dalam mika Small.
* Apel dapat dijual dalam mika Medium.
* Apel dapat dijual dalam mika Big.
* Apel dapat dijual dalam kotak.

Dengan demikian, harga dan stok dapat berbeda untuk setiap variasi.

## 2.2 Tujuan Tambahan

Sistem menyediakan:

* Authentication menggunakan Google.
* Keranjang belanja.
* Checkout.
* Pembayaran QRIS.
* Pembayaran COD.
* Transfer dengan upload bukti pembayaran.
* Manajemen status pembayaran.
* Riwayat transaksi.
* Dashboard penjualan.
* Grafik penjualan.

```text

    ↓

    ↓

    ↓
```

```text

├── Mika Small
├── Mika Medium
├── Mika Big
├── Kotak
```

# 12. Product Variant

Product Variant adalah inti sistem produk.

Contoh:

```text
Apel
│
├── Mika / Small / Pcs
├── Mika / Medium / Pcs
├── Mika / Big / Pcs
├── Kotak / null / Box
└── Tanpa Kemasan / null / Kg
```

Field:

| Field             | Tipe                 |
| ----------------- | -------------------- |
| id                | bigint               |
| product_id        | foreign key          |
| packaging_type_id | foreign key nullable |
| size_id           | foreign key nullable |
| unit_id           | foreign key          |
| sku               | varchar unique       |
| price             | decimal              |
| stock             | decimal              |
| is_active         | boolean              |
| timestamps        | datetime             |

## Contoh

```text
SKU: APL-MED-001

Produk:
Apel

Kemasan:
Mika

Ukuran:
Medium

Satuan:
Pcs

Harga:
15000

Stok:
20
```

# 13. Aturan Produk

Sistem harus memungkinkan variasi yang berbeda untuk produk yang sama.

Contoh:

| Produk | Kemasan | Ukuran | Satuan |  Harga |
| ------ | ------- | ------ | ------ | -----: |
| Apel   | Mika    | Small  | Pcs    | 10.000 |
| Apel   | Mika    | Medium | Pcs    | 15.000 |
| Apel   | Mika    | Big    | Pcs    | 20.000 |
| Apel   | Kotak   | -      | Box    | 35.000 |
| Apel   | -       | -      | Kg     | 30.000 |

Tidak semua produk wajib memiliki:

* Kemasan.
* Ukuran.

Tetapi setiap variant harus mempunyai satuan.

---

# 14. Stok

Stok disimpan pada level `product_variant`.

Contoh:

```text
Apel Mika Small
Stok: 20 Pcs

Apel Mika Medium
Stok: 15 Pcs

Apel Kg
Stok: 50 Kg
```

Dengan demikian stok tidak bercampur antara Pcs, Box, dan Kg.

## Aturan Stok

Saat transaksi berhasil dibuat:

```text
stok variant
    ↓
dikurangi
    ↓
quantity transaksi
```

Sistem harus memastikan stok mencukupi sebelum checkout.

Contoh:

```text
Stok: 10

Customer membeli:
3

Sisa:
7
```

# 17. Metode Pembayaran

Sistem memiliki tiga metode pembayaran:

```text
QRIS
COD

```

---

# 18. Pembayaran QRIS

Untuk versi pertama, QRIS menggunakan QRIS statis.

Flow:

```text
Checkout
    ↓
Pilih QRIS
    ↓
Tampilkan QRIS
    ↓
Customer melakukan pembayaran
    ↓
Customer mengupload bukti pembayaran
    ↓
Status:
WAITING_VERIFICATION
    ↓
Admin melakukan verifikasi
    ↓
PAID
```

QRIS belum menggunakan payment gateway otomatis.

---

# 19. Pembayaran COD

Flow:

```text
Checkout
    ↓
Pilih COD
    ↓
Buat pesanan
    ↓
Status pesanan
PROCESSING
    ↓
Barang dikirim
    ↓
Customer membayar
```

Status pembayaran awal:

```text
PENDING
```

Setelah pembayaran diterima:

```text
PAID
```

---

# 20. Transfer Bank

Flow:

```text
Checkout
    ↓
Pilih Transfer
    ↓
Tampilkan informasi rekening
    ↓
Customer melakukan transfer
    ↓
Upload foto bukti transfer
    ↓
WAITING_VERIFICATION
    ↓
Admin memeriksa
```

Jika valid:

```text
PAID
```

Jika tidak valid:

```text
REJECTED
```

Customer dapat melakukan upload ulang jika transaksi masih diperbolehkan.

---

# 21. Bukti Pembayaran

Untuk QRIS dan Transfer, customer dapat mengupload foto bukti pembayaran.

Field:

```text
payment_proof
```

Format yang diperbolehkan:

```text
JPG
JPEG
PNG
WEBP
```

Batas ukuran file harus ditentukan pada konfigurasi aplikasi.

---

# 22. Status Pembayaran

Status pembayaran:

```text
PENDING
WAITING_VERIFICATION
PAID
REJECTED
EXPIRED
CANCELLED
```

## Penjelasan

### PENDING

Transaksi dibuat tetapi belum melakukan pembayaran.

### WAITING_VERIFICATION

Customer sudah mengirim bukti pembayaran dan menunggu pemeriksaan admin.

### PAID

Pembayaran sudah diverifikasi.

### REJECTED

Bukti pembayaran ditolak.

### EXPIRED

Transaksi melewati batas waktu pembayaran.

### CANCELLED

Transaksi dibatalkan.

# 24. Sale Items

Detail produk yang dibeli disimpan pada:

```text
sale_items
```

Field:

| Field              | Tipe        |
| ------------------ | ----------- |
| id                 | bigint      |
| sale_id            | foreign key |
| product_variant_id | foreign key |
| product_name       | varchar     |
| variant_name       | varchar     |
| quantity           | decimal     |
| price              | decimal     |
| subtotal           | decimal     |
| timestamps         | datetime    |

Nama dan harga sebaiknya disimpan sebagai snapshot transaksi.

Tujuannya agar perubahan nama/harga produk di kemudian hari tidak mengubah histori transaksi.

Contoh:

```text
Saat transaksi:
Apel Mika Medium
Rp15.000
```

Jika admin kemudian mengubah harga menjadi:

```text
Rp18.000
```

Transaksi lama tetap:

```text
Rp15.000
```

```text

   ↓

   ↓
Google OAuth
   ↓
Google memberikan identity
   ↓
Laravel
   ↓
Cari email / google_id
   ↓
User ditemukan?
   ├── Ya → Login
   └── Tidak → Buat User
```

Data user minimal:

```text
name
email
google_id
avatar
```

Email Google menjadi identitas utama user.

# 39. Business Rules

## BR-001

Customer harus login sebelum melakukan checkout.

## BR-002

Customer dapat melihat produk aktif tanpa login.

## BR-003

Produk nonaktif tidak dapat dibeli.

## BR-004

Variant nonaktif tidak dapat dibeli.

## BR-005

Harga transaksi harus dihitung oleh backend.

## BR-006

Stok harus diverifikasi saat checkout.

## BR-007

Quantity dapat menggunakan decimal.

## BR-008

Transfer membutuhkan bukti pembayaran.

## BR-009

QRIS membutuhkan bukti pembayaran untuk versi pertama.

## BR-010

COD tidak membutuhkan bukti pembayaran saat checkout.

## BR-011

Hanya admin yang dapat memverifikasi pembayaran.

## BR-012

Customer hanya dapat melihat transaksi miliknya.

## BR-013

Transaksi yang sudah PAID tidak boleh diubah secara bebas.

## BR-014

Harga pada `sale_items` merupakan snapshot harga ketika transaksi dibuat.

## Authentication

* User lama dapat login kembali.
* User dapat logout.

## Produk

* Variant dapat memiliki ukuran.

* Customer dapat mengubah quantity.

* Customer dapat memilih QRIS.
* Customer dapat memilih COD.
* Customer dapat memilih Transfer.
* Transfer dapat upload bukti.
* QRIS dapat upload bukti.

* Total penjualan ditampilkan.

# 43. Prinsip Pengembangan

Sistem harus dibuat dengan prinsip:

### Simple

Jangan membuat modul yang belum diperlukan.

### Flexible

Produk harus mendukung variasi:

```text
Kemasan
Ukuran
Satuan
```

### Secure

Semua transaksi dan pembayaran harus diverifikasi oleh backend.

### Maintainable

Business logic penting ditempatkan pada Service, bukan seluruhnya di Controller.

### Scalable

Struktur database harus memungkinkan penambahan payment gateway dan fitur lain pada versi berikutnya tanpa melakukan perubahan besar.

# 45. Kesimpulan

Sistem Penjualan Buah menggunakan struktur produk yang fleksibel.

Konsep utama:

```text
PRODUCT
   ↓
PRODUCT VARIANT
   ↓
┌──────────────┐
│ Kemasan      │
│ Ukuran       │
│ Satuan       │
│ Harga        │
│ Stok         │
└──────────────┘
```

Penjualan:

```text
Product
   ↓
Variant
   ↓
Cart
   ↓
Checkout
   ↓
Payment
   ├── QRIS
   ├── COD
   └── Transfer
          ↓
      Bukti Foto
          ↓
      Verification
```

Teknologi:

```text
Laravel 13
React
Inertia.js
MySQL
Google OAuth
```

Target utama versi pertama adalah **sistem penjualan buah yang sederhana, fleksibel terhadap variasi produk, memiliki tiga metode pembayaran, dan menyediakan dashboard/grafik penjualan.**
